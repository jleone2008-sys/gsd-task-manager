2026-06-03Quota-habit streaks are now event-based (consecutive met periods, extras don't count). Two iterations same day. (1) The original x_per_week/x_per_month streak counted consecutive fixed Mon–Sun weeks / calendar months that met quota — which reset on rest days mid-week and broke when sessions straddled a Sunday→Monday boundary. (2) First fix tried a day-by-day rolling window (consecutive days whose trailing 7/30d held the quota) — but that reads as a day count, so a 1×/month "Finished Book/Podcast" showed a nonsensical 121. (3) Final model (shipped): streak counts EVENTS, by period. The current in-progress period contributes its completions so far capped at the quota (extras don't count) and never breaks the streak; then walk back through fully-elapsed periods, each met period adding quota events, stopping at the first elapsed period that fell short. So 3×/week: a week with 4 done counts 3; next week with 2 logged so far shows 3+2 = 5; a week that closes at 2/3 drops that week's contribution. Rest days inside a period never drop it — only a closed period under quota does. Rewrote computeStreak + computeBestStreak quota branches in 03-habits-core.js with period helpers quotaPeriodRange (Mon–Sun week / calendar month) + shiftQuotaPeriod; best-streak = peak running value (run-of-met-periods×quota + capped current), always ≥ current. Strict cadences (daily/weekdays/custom) unchanged; isQuotaMet still drives due-today + scoring. Verified against real prod data: "Lift Weights" (3×/wk) = 4 (3 from last met week + 1 this week), "Finished Book/Podcast" (1×/mo) = 4 (Feb–May met), plus the 4-done→3 and prior+2→5 hypotheticals — all confirmed end-to-end via the in-app functions in mock, no console errors. Shipped 2026-06-03 — not yet deployed (the rolling-window interim is currently live in prod showing the inflated day-counts; this commit should be pushed to replace it).

🧠 Learnings & non-visualized context

Invisible-but-important conventions. The kind of thing that's easy to violate by accident if you don't know it.

  • Theming = token overrides on <html>; build new UI with tokens, never hex. The Appearance feature re-themes the app via four data-* attributes (data-palette/data-corners/data-type/data-cards) on <html> that override :root tokens (the THEMING block in app.css). Any component built on --bg/--surface/--ink*/--guava-*/--r-*/--font-sans themes automatically; hardcoded hex will NOT follow the palette. Accent = --guava-* (palette-driven, hue varies). Destructive/danger/overdue/error = --danger-* (fixed red). Never use guava for a delete/error surface — it turns green/blue under Sage/Sky. Semantic colors (earth chips, rings, today/later/done status) are intentionally not themed. Persisted in user_settings.appearance; cached in localStorage.gsd_theme and applied pre-paint by the inline script in app.html (don't remove it — it prevents a flash of the default theme).
  • Where shared constants/config live (use these, don't re-hardcode). Design values: tokens in app.css :root + documented in brand-framework.html — including --scrim/--scrim-blur (every modal backdrop) and --accent-blue-rgb (interactive-blue, used as rgba(var(--accent-blue-rgb), x)). Backend: netlify/functions/lib/models.js (AI model names), lib/time.js (HOUR_MS/DAY_MS/WEEK_MS), lib/health.js (RECOVERY_STALE_HOURS), plus the existing lib/http|auth|encryption|supabase. Frontend cross-script globals live in beta/src/01-core.js (loaded before all other app scripts): HOUR_MS/DAY_MS/WEEK_MS, RENDER_DEBOUNCE_MS. Per-call values that legitimately vary (e.g. Claude max_tokens per task, overlay opacity per element) intentionally stay at the call site.
  • Mood scale: 1 = Bad, 5 = Great. Lower number is worse, higher is better. After the invert_mood_scale migration. See netlify/functions/lib/mood-scale.js for the canonical mapping. Functions sending mood to Claude should translate the integer to a label and include the scale note explicitly — otherwise Claude defaults to "higher is worse" and confidently reports backwards.
  • Oura date convention: oura_daily.date = X represents the sleep that ENDED on date X. So today's row contains last night's sleep. The brief's "recovery" block reads today's row; the "activity" block reads yesterday's row (activity_score on date X = the day X ending). Phase 1.6 fixed a bug where the brief read yesterday's row for sleep and showed stale numbers.
  • Whoop V2 + BYO model. Each user creates their own developer app at developer.whoop.com. Whoop rotates the refresh token on every exchange. V1 (/developer/v1/*) was deprecated late 2025; V2 keeps the /developer/ prefix at /developer/v2/* (NOT at the root — assuming root /v2/* caused a 404 regression, fixed 2026-05-28). Response shapes mostly unchanged but pagination key shifted from next_token to nextToken in some endpoints — whoopPaginate accepts either defensively.
  • Phase 2b (ES modules) was abandoned. Attempted 2026-04-21, hit runtime cycle issues, reverted. Do NOT retry mechanically; the existing classic-script-with-global-scope shape is intentional even though it looks dated.
  • Beta is canonical /app. What was at /beta/app now lives at /app. Old beta URLs 301-redirect. Legacy 2.5k-line SPA archived to /legacy-app.html for rollback. App features go in app.html; index.html is the marketing page.
  • localStorage is never primary store. Per feedback_long_term_best_practice memory. Always do it the proper long-term way; localStorage is for ephemeral UI state only (e.g. workout draft autosave).
  • Compound primaries are locked in the workout tuner. See COMPOUND_PRIMARIES in netlify/functions/lib/exercise-taxonomy.js. Substring match is case-insensitive; "bench press", "deadlift", "back squat", "overhead press", "barbell row", "pull-up", "lat pulldown", "dips" and variants are off-limits to the tuner. Accessory-only refinement keeps strength curves intact (Helms weak-link principle).
  • Repos always stay private. Per global instruction. Never propose making a repo public — for any reason. If a build tool needs access, use the proper auth path (Cloud Build GitHub App, deploy keys, PATs, GitHub App tokens).
  • Production-first validation. Per global instruction. Deploy directly to prod (Vercel, Cloud Run, Supabase, Netlify) and validate there. No "let's run this locally first to confirm" hybrid phases. Vercel env vars + cloud Secret Manager hold credentials.
  • AI build speed: same-day completion is the default assumption. Per global instruction. A worker module is an hour, a connector is 30 minutes, a feature is a couple of hours. Don't pad estimates with human-team scales. The only things that take real wall-clock time: vendor sales cycles, external account approvals, burn-in periods that require accumulating real-world data, and human review windows when Joe explicitly wants thinking time.
  • Brief in two modes per local day. Morning brief = 04:00-16:00 local; evening = 16:00-04:00. Each gets its own row in daily_briefs via the (user_id, brief_date, mode) UNIQUE. normalizeMode derives the right mode from the user's timezone.
  • Sleep button window: 20:00-04:00 local. Outside that, briefSleepButtonVisible() returns false and the head-strip slot collapses. The brief's right-side slot otherwise carries the weather chip (morning) or is empty (evening).
  • Brief-recommendation signatures. bedtime_target:HH:MM for sleep targets; plan_tune:<ops>_for_<focus> for workout tunes; plan_tune:rejected:<code> for tuner policy violations; plan_tune:abstain for tuner abstain decisions. The efficacy view groups by (user, signature, variant) so deterministic and A/B outcomes don't mix.
  • Netlify sync functions: await your persists. Fire-and-forget promises (foo(...).catch(...)) at the end of a handler can be torn down before they resolve when Lambda recycles the execution context. The workout_sessions.ai_feedback bug came from this pattern. Pattern to use: await persist(...) inside a try/catch so the response still ships even if the persist fails. For genuinely long writes, use a background function (*-background.js) instead.
  • Dev mock-mode hinges on script load order + a prod-strip build step. beta/src/dev/fixtures.js and mock-mode.js MUST stay loaded (deferred) before beta/src/01-core.js in app.html — mock-mode overrides supabase.createClient(), and 01-core calls it at eval time to build the const db. Reorder them after 01-core and the stub never installs. The two tags live inside <!-- DEV-MOCK-MODE:start … :end --> markers; netlify.toml now has a [build] command = "node scripts/inject-dev-mode.mjs" that strips that block only when CONTEXT==='production' (publish dir stays repo root; functions still auto-detected). Don't remove the markers, the build command, or the gate in mock-mode.js without understanding all three — prod safety is layered across them.
  • PostgREST silently down-casts objects to text for text columns. If you POST {"foo": {"bar": 1}} and column foo is text, it stores '{"bar": 1}' (a string). The reader gets a string back, not an object. Lesson: when a column holds structured data, make it jsonb. Cast loss-of-fidelity is silent on write but breaks the read path.

🔮 Open questions & known weirdness

  • Whoop V2 response-shape verification. After deploy, the first nightly Whoop sync will log field-key arrays to Netlify console. If field names differ from the V1 accessors (e.g. recovery_score nested under a different sub-object), the existing field extraction will produce nulls. Watch the first run's logs; patch syncWhoopUser accessors if needed. Remove the probe console.log lines after one clean run.
  • Plan-tune efficacy needs n_proposed ≥ 3 per signature. Weekly synthesis prompt explicitly skips surfacing patterns when fewer (cold start protection). At monthly cadence + signature granularity, this means the first plan-tune patterns won't appear in weekly synthesis until ~3-4 months in. Not a bug — just a long warm-up.
  • Sleep-intent visualization deferred. Data accumulates passively; surfacing waits on ~14 paired observations before a "settle time" stat is honest.
  • Refresh button on preliminary brief re-pulls Oura. User-initiated refresh on a preliminary brief calls beta-sync-now?provider=oura&days=2 before the brief regen. If the user pulls the brief 5+ times in a row, that's 5 Oura re-pulls. Soft rate-limit on the Oura side may eventually throttle; not seen in practice but worth knowing.
  • Goal-aware tuning not modeled. Tuner reads body_comp_goals as context but treats bulk/cut/recomp identically. Cut phases would ideally tighten the +20% volume cap; bulks might loosen it. Hold until evidence accumulates.
